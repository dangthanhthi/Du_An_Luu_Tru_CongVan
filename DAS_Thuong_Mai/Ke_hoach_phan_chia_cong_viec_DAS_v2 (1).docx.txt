KẾ HOẠCH PHÂN CHIA CÔNG VIỆCXÂY DỰNG LẠI HỆ THỐNG DAS
1. Mục tiêu và nguyên tắc làm lại DAS
Nhóm sẽ xây dựng lại DAS nhưng giữ các nghiệp vụ cốt lõi về công văn đến, công văn đi, công văn nội bộ, đối tác, tập tin và phân quyền. Phiên bản mới đồng thời phải tiếp nhận DB cũ làm nguồn dữ liệu migration, áp dụng cơ chế Authentication/SSO theo EAP và hỗ trợ các yêu cầu nghiệp vụ mới trong Requirement v2.
Không thiết kế app mới chỉ để khớp nguyên trạng DB cũ. Có thể thêm, đổi hoặc tách cấu trúc dữ liệu nếu requirement mới cần.
Mọi thay đổi schema phải có mapping và cơ chế migrate dữ liệu cũ sang cấu trúc mới một cách kiểm chứng được.
Authentication mới không tiếp tục dựa trên cơ chế custom cũ; phần đăng nhập phải tích hợp OIDC SSO của EAP bằng thư viện/framework chuẩn.
Authorization nghiệp vụ của DAS vẫn phải được giữ ở ứng dụng: role, department, sensitivity, ownership, document scope và delegation.
Các thành viên chỉ bắt đầu code sâu sau khi chốt data contract, role model và service ownership để giảm conflict.

2.2. Requirement v2 – nghiệp vụ mục tiêu
Hai pháp nhân Hoàng Long (HL) và Hoàn Vũ (HV), đồng thời có trường hợp chung HLHV.
Incoming: nhận từ email/fax theo chu kỳ, cho phép đăng ký thủ công, AI hỗ trợ nhận diện sender, chọn nhiều đơn vị nhận, có related outgoing.
Outgoing: thư ký phòng đăng ký, có inputter/originator, gửi nhiều External Entity, có related incoming.
Internal: không gửi đối tác bên ngoài, chỉ gửi Ban lãnh đạo.
Document number theo format riêng cho Incoming/Outgoing/Internal và số thứ tự reset hằng năm.
External Entity CRUD nhưng soft delete.
Weekly reminder cho document quá 1 tuần chưa completed.
Task Management integration: một document có nhiều task; DAS tạo task qua API TMS và hiển thị assignee/status/deadline.
Phân quyền mới dựa trên role + department + sensitivity + ownership; role gồm GM, DGM, LM, DLM, Group TV1er, Staff, Secretary GM.
2.3. EAP – tích hợp bắt buộc/được cấp
OIDC SSO: Authorization Code Flow + PKCE S256; endpoint phải lấy từ discovery, không hard-code.
API token validation: JWT/JWS RS256, validate signature, iss, aud, exp, nbf; dùng JWKS và kid.
RabbitMQ User Sync & Lifecycle: nhận assigned users và các event deleted/restored/replaced; consumer phải idempotent và ACK sau commit.
Delegation là capability bắt buộc: nhận preparation/cancellation event, lưu local projection, publish Ready/Failed và authorize delegated request theo claims.
Notification và Storage là optional services: chỉ tích hợp nếu EAP provision cho application/environment.
Không commit secret/token; configuration phải tách theo environment.

4. Chiến lược dữ liệu và migration
4.1. Nguyên tắc
Snapshot/backup DB cũ và không thực hiện migration trực tiếp trên dữ liệu duy nhất.
Thiết kế schema target từ requirement mới; không copy toàn bộ field legacy nếu không còn nghiệp vụ sử dụng.
Lập mapping table-by-table và field-by-field trước khi viết migration.
Giữ khóa truy vết legacy (ví dụ LegacyId/LegacySource) nếu cần đối soát.
Migration phải rerunnable hoặc có checkpoint rõ ràng; không tạo duplicate nếu chạy lại.
Có report sau migration: source count, migrated count, skipped count, failed count và lý do.
Kiểm tra referential integrity, document number, relationship, attachment reference và quyền truy cập sau migration.

5.1. Thành viên 1: Database, Architecture, Migration & Core Rules
Phân tích đầy đủ DB cũ: bảng, dữ liệu, quan hệ ngầm, dữ liệu bắt buộc giữ và dữ liệu legacy không còn dùng.
Thiết kế schema target theo Requirement v2 + EAP, sau khi thống nhất target DB engine với mentor.
Chốt service ownership và data contract giữa Auth/Identity, Document, Partner, Files, Worker và TMS integration.
Thiết kế model LegalEntity (HL/HV/HLHV), Department, Sensitivity, document relationships và numbering.
Thiết kế document number generator có concurrency safety và reset đúng scope theo năm.
Lập mapping migration, migration audit và validation report.
Chuẩn bị migration dry-run trên bản copy của DB cũ; không migrate production ngay.
Review PR của 2 thành viên còn lại, xử lý conflict contract và integration cuối.
Chốt Definition of Done và regression checklist.
Deliverables của Thành viên 1:
ERD/schema target v1.
Old → New migration mapping document.
Danh sách API/domain contracts dùng chung.
Document numbering specification + test cases.
Migration script/tool + migration validation report.
Architecture diagram cập nhật có EAP và TMS.
Integration checklist và release checklist.
5.2. Thành viên 2: Authentication Framework + EAP Integration
Chọn/triển khai thư viện OIDC chuẩn trong .NET theo profile EAP được cấp; dùng Authorization Code Flow + PKCE.
Không hard-code endpoint; dùng discovery document.
Xử lý callback/login/logout/local session theo kiến trúc đã chốt; validate state/nonce.
Cấu hình API JWT/JWKS validation RS256: signature/kid, issuer, audience, exp, nbf.
Xây local user projection theo EAP userId; phối hợp migration user cũ với Thành viên 1.
Implement RabbitMQ consumer cho assigned users và identity lifecycle events; idempotent, deduplicate, ACK sau commit.
Publish sync result cho các event có result contract.
Implement delegation preparation/cancellation projection và Ready/Failed flow.
Validate delegated token claims và audit actor/subject riêng; không copy role/grant của delegator sang delegate.
Xây authorization policy primitives để Document Service có thể kiểm tra role, department, sensitivity và ownership.
Viết integration tests cho login/token validation/user sync/delegation.
Deliverables của Thành viên 2:
OIDC/EAP configuration template theo environment (không chứa secret thật).
Identity integration module/service.
RabbitMQ consumers + idempotency storage.
Delegation projection + authorization helpers.
Role/policy mapping document.
Test matrix cho GM/DGM/LM/DLM/Group TV1er/Staff/Secretary GM với Normal/Confidential.
5.3. Thành viên 3: Document Workflows, Automation & TMS Integration
Refactor/implement Incoming workflow theo schema mới: manual register, email/fax intake, one PDF, sender/partner, recipient list, related outgoing.
Refactor/implement Outgoing workflow: inputter/originator, department, multiple External Entities, related incoming, file, status Distributed.
Refactor/implement Internal workflow theo numbering và TV1ership scope.

TMS integration: create task từ document, lưu reference cần thiết, lấy/hiển thị assignee/status/deadline; xử lý lỗi/timeout/idempotency.
Giữ AI-OCR ở vai trò integration: gọi OCR pipeline, map kết quả vào draft metadata và cho user review; không tự ý đổi OCR engine nếu không được giao.
Phối hợp với Thành viên 2 để áp authorization filters vào query/document/file access.

9. Regression test tối thiểu phải có
Data migration: incoming/outgoing/internal/partner/user/department; kiểm tra record count và sample quan hệ.
Numbering: đổi năm, nhiều request đồng thời, HL/HV/HLHV, outgoing/internal theo department.
Authorization: GM/DGM/Secretary GM toàn quyền; LM/DLM/Group TV1er theo phòng; Staff Normal theo phòng; Staff Confidential theo ownership theo requirement.
Delegation: đúng actor/subject, hết hạn, cancelled, version mismatch, duplicate event.
Incoming recipients nhiều phòng/đơn vị; related outgoing.
Outgoing nhiều partner; inputter tạo giùm originator; related incoming.
File access: biết file id nhưng không có document scope thì phải bị từ chối.
Email scanner: email duplicate, attachment thiếu/sai, job chạy lại.
Reminder: >1 tuần, điều kiện completed, recipient To/CC.
TMS: task creation idempotency, TMS timeout/down, status mapping.
EAP token: issuer/audience sai, expired/not-before, unknown kid, HMAC/none algorithm phải reject.
10. Các quyết định phải hỏi/chốt trước khi bắt đầu code sâu
Target database engine của app mới là SQL Server, MariaDB hay engine khác? File legacy là MariaDB; không được tự suy đoán.
Auth framework cụ thể: ASP.NET Core OIDC middleware + local Identity projection, ASP.NET Core Identity, hay BFF pattern nào được mentor yêu cầu?
EAP client profile của DAS là Confidential Web/BFF hay Public SPA? Client authentication method nào được provision?
EAP có provision Notification và Storage cho DAS không? Hai capability này là optional trong guide.
Role từ EAP có authoritative cho DAS hay DAS giữ local role/access mapping riêng? Semantics nào được đăng ký với EAP?
Department/OU lấy từ local DB hay EAP Organization Context API? Guide nói không suy ra Department từ user-sync payload.
Contract cụ thể của Task Management API: create endpoint, auth, idempotency, task id, status values, deadline format.
File binary của legacy app hiện nằm ở đâu và path doc_file trong dump map tới storage nào? SQL dump chỉ có reference/path, không chứa file PDF.
Quy tắc chính xác cho 'completed' và weekly reminder khi document bị Cancelled hoặc thiếu một trong các field.
Quy tắc Group TV1er ở Confidential trong bảng requirement chưa thể hiện đầy đủ; cần mentor xác nhận.
11. Quy ước làm việc nhóm đề xuất
Mỗi Epic có branch/PR riêng; không commit trực tiếp vào main.
Mọi thay đổi schema phải kèm migration + mapping note + rollback/forward plan.
Không đổi API contract dùng chung nếu chưa thông báo hai thành viên còn lại.
PR chạm Auth/Authorization hoặc Migration phải được Thành viên 1 review.
Không commit .env, EAP secret, JWT/token, RabbitMQ password, DB credential.
Mỗi task đóng phải có test evidence hoặc log/screenshot đủ để người khác tái kiểm tra.
Các giả định chưa được mentor xác nhận phải ghi rõ TODO/Decision, không biến thành business rule ngầm.
